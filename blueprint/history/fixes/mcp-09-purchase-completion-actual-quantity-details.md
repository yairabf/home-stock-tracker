## Goal

Let `complete_grocery_purchase` record actual purchased quantity and unit when
the user explicitly supplies them, while preserving atomic grocery completion,
safe stale-state handling, and the existing ID-only call during a documented
transition. Actual measurements must never be inferred from requested grocery
measurements.

## Repository findings

- The defect exists at current commit
  `c0c0f2854e2320fc299ac603c21493256dfaaf6f` and baseline
  `4058dc2fdcb65a34c4ba0a9082b030d9ab4c7c96`. The current MCP schema accepts
  only `groceryItemIds`, and `InventoryService.completeGroceryPurchase()`
  creates one `PURCHASED` event per distinct product with null `quantity` and
  `unit`.
- The shared service already owns pending-item validation, request-order
  preservation, one Prisma transaction, guarded pending-item updates, and
  rollback on a concurrent winner. The MCP handler is thin and supplies generic
  `mcp` provenance. This service is the correct owner for measurement validation
  and event aggregation.
- `InventoryEvent` already has nullable `quantity` and `unit` columns, and its
  response and history contracts already expose both fields. No database
  migration or persisted-data rewrite is needed.
- A separate REST route, `POST /api/v1/inventory/purchases/complete`, already
  records one optional quantity and unit for a single product. It uses another
  `InventoryService` method. This fix does not need a new REST route, but the
  existing REST suite remains regression evidence that both transports retain
  their supported completion behavior.
- Multiple pending rows can reference one product. Creating one event per row
  would make one shopping trip look like several purchases to
  `StatisticsService`, which calculates purchase intervals and typical quantity
  from event rows. The coherent rule is one event per selected product: sum only
  explicitly supplied quantities whose trimmed units match exactly, and reject
  ambiguous groups before writing.
- The canonical agent instructions live in
  `integrations/shared/home-stock-tracker/`; Hermes and OpenClaw files are
  generated by `npm run skills:generate`. Current instructions send only IDs and
  must be updated after the service and MCP contracts are locked.
- MCP validation and domain failures already become safe tool errors, unexpected
  failures are sanitized, and uncertain mutations are not retried by agent
  instructions. Those conventions remain unchanged.

## In scope

- Extend the shared grocery-purchase completion input with selected item objects
  carrying optional actual quantity and unit.
- Keep the existing `groceryItemIds` input as a documented legacy path during
  the transition.
- Validate actual measurements in the shared application service, not only in
  the MCP adapter.
- Aggregate actual quantities once per product only when every selected row for
  that product has an explicit quantity and the trimmed units match exactly.
- Reject mixed measured/unmeasured rows or conflicting units for one product
  before starting a transaction.
- Preserve atomic event creation and guarded grocery-item completion under stale,
  repeated, and concurrent requests.
- Prove the published schema and behavior through real in-memory and
  authenticated Streamable HTTP MCP clients, including persistence-backed
  regression coverage.
- Update canonical agent instructions, generated Hermes/OpenClaw bundles,
  scenarios, contract tests, API/integration documentation, and the project
  overview.

## Out of scope

- Copying `requestedQuantity` or grocery `unit` into an actual purchase event.
- Automatically converting, case-folding, singularizing, or otherwise
  reconciling units.
- Updating requested grocery quantities or units during purchase completion.
- Adding a shopping-trip model, idempotency key, receipt ingestion, barcode
  ingestion, UI, store integration, or new infrastructure.
- Reworking the legacy REST completion and partial-completion routes unless a
  shared-domain regression is discovered during implementation.
- Solving the broader MCP capability/version probe in MCP-11. This transition

## Data / contracts

No Prisma schema or migration change is planned.

The unchanged legacy MCP request remains accepted:

```json
{
  "groceryItemIds": ["uuid-1", "uuid-2"]
}
```

The preferred additive request is:

```json
{
  "items": [
    {
      "groceryItemId": "uuid-1",
      "actualQuantity": 2,
      "actualUnit": "cartons"
    }
  ]
}
```

Load-bearing rules:

- The top-level object is strict and must contain exactly one of
  `groceryItemIds` or `items`. Each selected grocery-item UUID must be unique,
  pending, and unlinked at the time its guarded update wins.
- `items` is non-empty. Each item object is strict and requires
  `groceryItemId`. `actualQuantity`, when present, is finite and greater than
  zero. `actualUnit`, when present, is trimmed, non-empty, and forbidden unless
  `actualQuantity` is also present.
- An item object containing only `groceryItemId` records no actual measurement.
  The service must not substitute its requested quantity, grocery unit, product
  typical unit, or any inferred value.
- For one selected product, if no rows supply `actualQuantity`, create one
  `PURCHASED` event with null quantity and unit, matching legacy behavior.
- For one selected product, if every row supplies `actualQuantity`, all trimmed
  `actualUnit` values must match exactly, including all being absent. Create one
  event whose quantity is the sum and whose unit is that shared value or null.
- If only some rows for a product supply actual quantity, or their units differ,
  reject the entire request with a stable safe domain error before the
  transaction. No unit conversion or case normalization is attempted.
- Event order follows each product's first appearance in the selected item
  order. Completed-item order follows request order. Every completed row links
  to its product's event.
- The transaction and guarded update remain the concurrency boundary. A repeat
  after success reports already resolved; a concurrent loser rolls back all
  events and item updates. Agents never retry an uncertain write automatically.
- `source` is never public input. The MCP adapter supplies `mcp`.
- Output shape remains `{ events, completedItems }`; measured events expose the
  stored `quantity` and `unit`, while completed grocery rows continue exposing
  their unchanged requested values.

Transition rules:

- Existing callers may continue using `groceryItemIds` during the transition.
- Skill bundle `1.10.0` and updated examples use `items` for all new calls,
  including item objects without measurement when the user gave none.
- Documentation labels `groceryItemIds` as legacy. Removal requires a later
  separately approved compatibility change after MCP-11 provides an
  authoritative capability/version contract.
